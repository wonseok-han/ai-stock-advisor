## PDCA 사이클 요약

### Plan 단계

**문서**: [docs/01-plan/features/timing-signal.plan.md](../../01-plan/features/timing-signal.plan.md)

**목표**: 진입 타이밍을 "팩트 기반으로 평가"하는 AI 분석 섹션 추가를 통해 서비스명과 일치하는 핵심 기능 제공

**주요 계획 항목**:
- 타이밍 판정: 3단계 (지금이니?! / 흠.. 애매한데? / 아직인듯?)
- 진입 조건 팩터: 10개 → 최종 8개 (가격 위치, 기술 지표, 거래량, 시장 환경, 밸류에이션)
- 예상 기간: 8일

### Design 단계

**문서**: [docs/02-design/features/timing-signal.design.md](../../02-design/features/timing-signal.design.md)

**설계 결정사항**:

| 영역 | 결정 | 근거 |
|------|------|------|
| **BE 아키텍처** | Gemini 프롬프트 스키마 확장 (ResponseValidator timing 파싱 추가) | 추가 API 호출 0, 기존 컨텍스트 재활용으로 토큰/비용 최소화 |
| **캐시 전략** | AI 응답 TTL 60분 → 120분 확대 | 타이밍 판정은 단기 변동성 높으므로 적절한 갱신 주기 |
| **캐시 버전닝** | `ind:v2:`, `ai:v3:` 적용 | stale data 회피, 코드 배포 시 캐시 자동 무효화 |
| **금지어 정책** | "매수 추천" 금지 → "조건 충족" 프레이밍 변경 | 법적 리스크 회피, 면책 일관성 |
| **FE 컴포넌트** | TimingCard 히어로 카드 (판정, 프로그레스바, 충족/미충족 리스트) | 사용자가 한눈에 진입 조건 파악 가능하도록 정보 계층화 |
| **배치 위치** | AI 분석 페이지 최상단 | 기존 시그널과 병렬 배치 (대체가 아닌 보완) |

## 학습 내역

### 잘된 점

1. **프롬프트 스키마 확장으로 추가 API 호출 제거**
   - 기존 Gemini 호출에 timing 섹션만 추가하여 토큰/비용 최소화
   - 기존 ContextAssembler의 지표/뉴스/가격 컨텍스트 100% 재활용

2. **Graceful degradation으로 안정성 확보**
   - timing 필드 누락/파싱 실패 시 null 반환 → 기존 시그널만 표시
   - 타이밍 판정 없어도 서비스 정상 동작 (하위 호환)

3. **면책 원칙 일관성**
   - "조건 충족 여부" 프레이밍으로 투자 자문 오해 방지
   - ForbiddenTermsRegistry가 timing 텍스트도 스캔하여 금지어 자동 검출

4. **캐시 최적화로 성능 향상**
   - TTL 120분 확대 + 버전닝으로 stale data 회피
   - 종목별 타이밍 판정 재계산 비용 감소

5. **사용자 피드백 수용**
   - 링크 카드 배지 제거 요청을 받아 바로 구현 (의도적 설계 편차)
   - UI 노이즈 최소화로 깔끔한 사용성 확보

### 개선할 점

1. **팩터 정합도 문제**
   - 설계에서 명시한 10개 팩터 → 최종 8개로 정리되는 과정에서 문서 동기화 시간 소모
   - 개선: Plan 단계에서 팩터 목록을 더 면밀히 검증

2. **P/E 평가 로직**
   - 설계: "섹터 평균 대비 할인"
   - 구현: "애널리스트 목표가 대비 할인 20%+"
   - 개선: 설계 단계에서 데이터 가용성을 더 조사해야 함

3. **프롬프트 테스트**
   - Gemini가 매번 일관된 형식으로 timing 필드를 반환하는지 검증하는 데 시간 소모
   - 개선: 프롬프트 확정 후 사전 테스트 10회 이상 실시 권장

4. **로딩 상태 관리**
   - AI 분석 페이지 진입 시 타이밍 카드의 스켈레톤이 필요했으나, 초기 구현에서 누락
   - 개선: FE 구현 전 로딩 상태 레이아웃을 설계 문서에 명시

### 다음에 적용할 사항

1. **PDCA 문서 동기화**
   - Plan → Design → Do 단계 진행 시 팩터/스키마 변경 사항을 즉시 문서에 반영
   - 최종 구현 전 디자인 문서 재검증 (다른 에이전트가 참고할 수 있도록)

2. **사용자 피드백 조기 수집**
   - 구현 중간(Do 단계 50% 완료 시점)에 스크린샷/프로토타입으로 사용자 피드백 수집
   - 배지 제거 같은 의도적 편차를 조기에 파악

3. **캐시 정책 선제적 수립**
   - 신규 AI 기능 추가 시 TTL/버전닝 전략을 Design 단계에서 명시
   - "기본값 60분" 정책을 넘어선 feature-specific 캐시 전략 수립

4. **법적 검증 조기화**
   - 프롬프트 확정 전 LegalGuardFilter 검사 수행 (사후 대응 아닌 사전 예방)
   - Prometheus 태그 정합을 구현 완료 후 추가하지 말고, 초기 설계에 포함
